# AGENTS.md – Инструкция для разработчиков

## Архитектура системы
- **Монорепозиторий с изоляцией**: `_core/master` (FastAPI + NiceGUI) и `_core/platform-cli` (CLI) разделены, но используют общие конфиги
- **Service discovery через файловую систему**: сканирование `services/{public,internal}/` каждые N секунд (watchdog)
- **Генерация конфигов Caddy из шаблонов**: Jinja2-шаблоны в `_core/caddy/templates/`; перезагрузка через API Caddy
- **Разделение public/internal**: internal сервисы не проксируются наружу, доступны только master service

## Основные компоненты
- **Master Service**: FastAPI + NiceGUI, основной сервис управления
- **Caddy**: reverse proxy для маршрутизации
- **Platform CLI**: утилита командной строки для управления сервисами
- **DockerManager**: управление контейнерами через aiodocker
- **HealthChecker**: HTTP probes с интервалом 30 секунд
- **BackupManager**: Kopia с дедупликацией

## Ключевые команды
- `./install.sh` - установка, генерирует конфигурационный файл `.ops-config.yml`
- `./restart_core.sh --build` - запуск core-сервисов (master + caddy)
- `make dev` - запуск master service в режиме разработки
- `make test` - запуск тестов
- `make test-cov` - тесты с покрытием кода

## Требования к окружению
- Docker ≥ 20.10.0 и Docker Compose ≥ 2.0.0
- Python 3.12 или 3.13 (для разработки)
- 4 ГБ ОЗУ минимум, 8 ГБ рекомендуется
- 10 ГБ свободного места на диске

## Особенности реализации
- **Health checks**: только HTTP GET, таймауты не настраиваются в коде (жестко закодированы)
- **Backup расписания**: используют croniter, но нет валидации синтаксиса cron
- **Отсутствие миграций БД**: используется SQLite (`master.db`) без Alembic; схема создается при старте
- **Логирование**: минимальное; логи Caddy могут быть отключены, логи приложения выводятся в stdout
- **Аутентификация**: поддержка Keycloak и built‑in auth, но переключение требует перезапуска

## Локальная разработка
- Локальные переопределения: `service.local.yml` (не коммитится), `.ops-config.local.yml`
- Для разработки используйте `make dev` или `./restart_core.sh --build`
- Используйте `ops list` для просмотра всех сервисов
- Используйте `platform` команды для полного функционала CLI

## Тестирование
- Трехуровневая система: unit → integration → full‑deploy‑cycle
- Асинхронные тесты (pytest-asyncio) с автоматическим режимом
- Интеграционные тесты используют Docker-in-Docker; проверьте доступность Docker socket

## Рекомендации при работе с сервисами
- Манифест `service.yml` должен содержать `health.endpoint`, иначе health check не будет работать
- Роутинг: выбрать один из типов: `domain`, `subfolder`, `port`; комбинирование не поддерживается
- Для внутренних сервисов используйте `services/internal/` директорию
- Используйте `service.local.yml` для переопределения настроек в локальной разработке

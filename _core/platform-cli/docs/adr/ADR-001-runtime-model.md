# ADR-001: Модель исполнения platform CLI v2 — синхронное ядро с потоковым параллелизмом

- **Статус**: accepted (2026-10-06, в рамках утверждённой спеки v1.2)
- **Связанные**: ADR-002, ADR-003; спека §10, §17.1 (N10)

## Контекст

CLI — one-shot процесс. Бюджеты: `status` ≤ 2с на 10 сервисов, параллельный
опрос источников обязателен (N10). Существующие драйверы данных синхронны:
docker SDK, subprocess (docker compose), questionary, rich. Единственный
асинхронный компонент — `api_client.py` (aiohttp + tenacity) для Master API.
Позже возможен Textual-dashboard (P7), который сам асинхронен.

Решение нужно принять до P1: от него зависит сигнатура use cases, адаптеров
и тестового каркаса.

## Решение

1. **Ядро синхронное** (use cases, домен, адаптеры — обычные функции).
2. **Параллелизм** — `concurrent.futures.ThreadPoolExecutor(max_workers=6)`
   внутри use cases (status/diag): секции и источники опрашиваются параллельно,
   результат — `SectionResult` на источник; дедлайн проверяется перед каждым
   вызовом адаптера (`Deadline.remaining()`), каждый docker/subprocess-вызов
   получает timeout ≤ остатку бюджета.
3. **master_source переписывается на requests + tenacity** (sync) — aiohttp
   из зависимостей v2 уходит. Ретраи только для идемпотентных методов, как
   в текущем клиенте.
4. **`--watch`** — синхронный цикл тиков (сборка → печать → sleep), перекрывающиеся
   тики пропускаются (§8.4).
5. Публичного asyncio API нет. Textual (P7, вне спеки) сможет вызывать
   синхронное ядро через workers (`thread=True`).

## Альтернативы

- **V2: asyncio-ядро** (use cases async, docker через `asyncio.to_thread`).
  Отклонено: асинхронность пронизывает все слои ради параллелизма 6–8
  источников; сложность тестов и кода растёт при ничтожной выигрыше latency;
  aiohttp оставался бы единственной причиной.
- **V3: последовательный опрос**. Отклонено: при 100–500мс на docker-вызов
  и 10 сервисах budget 2с нарушается уже на services+health (спека §17.1).

Сравнение (веса: совместимость 5, простота 4, производительность 3,
обратимость 3, расширяемость 2): V1 = 19, V2 = 12, V3 = 16.

## Последствия

**Положительные**: простота и читаемость ядра; потокобезопасность нужна только
внутри адаптеров (адаптеры не шарят изменяемое состояние); тесты без async;
tenacity работает в sync-режиме из коробки.

**Отрицательные**: параллелизм ограничен потоками (достаточно для I/O-bound);
будущие async-only интеграции потребуют моста.

**Нейтральные**: ThreadPoolExecutor создаётся на вызов команды (не процесс);
`docker` SDK-клиент — на поток с таймаутом.

## Проверка ограничений

- N10 (параллельный опрос) — выполняется (Executor).
- N1 (status ≤ 2с) — обеспечивается дедлайном + timeout на каждый вызов;
  остаточный риск: вызов не прерывается мгновенно, только по timeout
  (принято, см. спека §17.1).
- Watch §8.4 — синхронный тик с пропуском перекрытий.

# ADR-002: Сборка зависимостей — явный Ctx в composition root, порты как Protocols

- **Статус**: accepted (2026-10-06)
- **Связанные**: ADR-001, ADR-003; спека §10.2, §10.3

## Контекст

Спека требует: composition root собирает реализацию один раз; тесты подменяют
порты, а не имена helper'ов CLI; никаких DI-фреймворков и универсального
registry. В v1 зависимости — модульные синглтоны (`get_config()` c lru_cache,
адаптеры импортируются напрямую), из-за чего тесты патчат
`apps_platform.cli.<helper>` и хрупки. Нужно конкретное решение «как именно
собираем» до P1.

## Решение

1. **`Ctx`** — frozen dataclass, собирается один раз в `cli.py` (composition
   root): `config`, `root`, `deadline_policy`, и адаптеры, типизированные
   портами: `discovery: ServiceDiscovery`, `docker: DockerReader`,
   `caddy: CaddyReader`, `master: MasterGateway`, `prober: HealthProber`,
   `locks: LockManager`, `cache: CacheStore`, `journal: Journal`.
2. **Порты** — `typing.Protocol` в `core/ports.py`. Порт заводится только на
   реальной границе (спека §10.2): перечисленные 8 — полный список; новые
   порты добавляются по той же проверке.
3. **Use cases — функции**: `cmd_status(ctx, StatusOpts) -> StatusResult`
   и т.д. в `commands/*.py`. Typer-обработчик в том же модуле: разобрать
   args → вызвать use case → отдать результат в renderer → маппинг ошибок
   (ADR-003).
4. **Тесты**: fake-реализации протоколов + конструирование `Ctx` с ними;
   subprocess-тесты идут через entry point `platform2`. Патчи внутренних
   имён CLI запрещены (линт-правило/код-ревью).
5. Глобальный mutable state запрещён; `lru_cache` допустим только для
   неизменяемых snapshot'ов внутри одного вызова.

## Альтернативы

- **Классы use cases с constructor-injection**: отвергнуто — церемония классов
  без выгоды для one-shot CLI; функции + Ctx проще и так же явно.
- **v1-стиль (синглтоны + monkeypatch)**: отвергнуто — причина хрупкости
  существующих тестов; нарушает требование спеки §10.2.
- **DI-фреймворк/registry**: отвергнуто спецификой (§10.2, «порты только на
  реальных границах»).

## Последствия

**Положительные**: все зависимости видимы в сигнатурах; подмена — конструктор
`Ctx` с fake'ами; composition root — единственное место знания о конкретных
адаптерах; порты документируют границы системы.

**Отрицательные**: `ctx` протаскивается явно через все вызовы (принятая цена);
новый адаптер = правка Ctx + composition root.

**Нейтральные**: количество портов фиксировано и мало (8); переименования
портов дешевле после фиксации.

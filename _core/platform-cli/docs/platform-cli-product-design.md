## 1. Краткое предложение

Platform CLI должен стать не набором команд над Docker и Master API, а надёжной
операторской консолью платформы. Он помогает пройти весь рабочий цикл:

```text
увидеть состояние -> понять причину -> безопасно изменить -> проверить результат
```

Продукт строится вокруг трёх свойств:

- **Правдивость.** CLI показывает источник и свежесть сведений, отличает «не
  настроено» от «не удалось проверить» и не выдаёт предположение за факт.
- **Управляемость.** Сервисами можно управлять напрямую через Docker/Compose,
  даже если Master API недоступен.
- **Предсказуемость.** Один и тот же ввод имеет понятный результат в терминале,
  CI и скрипте; вопросы и подтверждения никогда не возникают неожиданно.

Первая версия остаётся текстовым CLI. Полноэкранный dashboard не является
предпосылкой хорошего UX и рассматривается только после получения опыта
использования базовых команд.

## 2. Видение продукта

### 2.1 Видение

Оператор должен понимать состояние платформы и безопасно выполнять повседневные
операции из терминала, не зная внутренних деталей Docker, Caddy и Master API.
Если центральный сервис управления недоступен, CLI продолжает выполнять локальные
операции и честно объясняет, какая информация временно недоступна.

### 2.2 Миссия

Сокращать путь от симптома до проверенного действия. CLI не просто сообщает, что
команда завершилась с ошибкой: он помогает понять, что известно, что не удалось
проверить и какой следующий шаг безопасен.

### 2.3 Продуктовая концепция

Platform CLI - это локальный операторский инструмент с двумя одинаково важными
режимами:

- **Работа человека:** ясное состояние системы, короткие объяснения, интерактивные
  подсказки при необходимости, наглядный прогресс и безопасные подтверждения.
- **Работа автоматики:** стабильные коды завершения, структурированный вывод,
  отсутствие неявного ввода и ограниченные по времени операции.

Режимы используют одни и те же сценарии приложения и модели данных. Это не две
отдельные реализации с разной логикой.

### 2.4 Для кого продукт

| Пользователь | Основная задача | Что считается хорошим результатом |
|---|---|---|
| Оператор платформы | Понять, что работает и что сломано | Один обзор с ясной свежестью данных и следующими действиями |
| Разработчик сервиса | Создать, задеплоить, проверить и изучить логи своего сервиса | Короткий и повторяемый рабочий цикл без знания устройства Master API |
| CI или скрипт | Запустить операцию и надёжно определить результат | Предсказуемые аргументы, JSON-контракт и exit code без prompt |

### 2.5 Не является целью

- Заменять Master Service или становиться отдельным планировщиком состояния.
- Автоматически исправлять конфигурацию без явного запроса оператора.
- Скрывать Docker или Master API за абстракцией, которая не добавляет устойчивости.
- Делать Textual/TUI обязательным для доступа к основным функциям.
- Дублировать авторитетные данные платформы локальным кэшем или догадками.

## 3. Модель опыта

Основной цикл пользователя состоит из четырёх фаз.

1. **Observe:** быстро получить сводку состояния через `platform status`.
2. **Explain:** увидеть, почему состояние неизвестно или проблемно, откуда взяты
   сведения и когда они были получены.
3. **Act:** выполнить явную операцию над конкретным сервисом или снапшотом.
4. **Verify:** увидеть результат операции и независимо проверить новое состояние.

Команды должны поддерживать этот цикл, а не требовать от пользователя помнить
предыдущий вывод или внутренние имена компонентов платформы.

Пример типового пути:

```text
$ platform status
Сервисы: 8 запущены, 1 требует внимания
api       running   health: failing   проверено 8s назад
Следующий шаг: platform service logs api --since 10m

$ platform service logs api --since 10m
...

$ platform service restart api
Перезапустить api? Будут перезапущены 2 контейнера. [y/N]

$ platform status api
api: running, health: healthy, проверено только что
```

Предложенные команды в выводе являются подсказкой, а не автоматическим действием.

## 4. Принципы продукта и UX

### 4.1 Сначала состояние, затем управление

`platform status` без аргументов всегда показывает обзор платформы. Он не открывает
выбор сервиса. `platform status <service>` показывает состояние выбранного сервиса.
Команды, изменяющие состояние, требуют явной цели.

### 4.2 Не скрывать неопределённость

Статус имеет как минимум состояние, источник, время наблюдения и признак
устаревания. `unknown` не используется как универсальная замена всем проблемам.
Примеры причин: `health не настроен`, `Master API недоступен`, `последняя проверка
3 мин назад`, `Docker Engine недоступен`.

### 4.3 Один сценарий, два интерфейса

Текстовый рендерер и JSON-рендерер получают один результат use case. JSON не
собирается отдельно из текста, а human output не является источником данных для
скриптов.

### 4.4 Вопросы только по делу

- Prompt разрешён только для отсутствующих значений в интерактивном терминале.
- `--no-input` гарантированно запрещает все вопросы.
- `--yes` пропускает только подтверждения. Он не выбирает сервис и не заполняет
  обязательные параметры.
- Если обязательного ввода нет, команда завершается с кодом аргументов и кратко
  показывает, как передать значение.
- Исключение: `platform status` без аргументов - полноценный сценарий просмотра,
  он никогда не требует выбора сервиса.

### 4.5 Подтверждение показывает последствия

Перед изменением CLI показывает объект, действие и значимые последствия. Для
восстановления backup явно указываются snapshot, целевой сервис и семантика
перезаписи. `--yes` пропускает диалог, но не заменяет параметры операции вроде
`--target` или `--force`.

### 4.6 Вывод без декоративного обязательства

Таблицы, цвета и Rich-компоненты применяются там, где они повышают читаемость.
Универсальная рамка не обязательна. Логи остаются построчными; узкий терминал не
должен превращать сводку в нечитаемый набор обрезанных колонок. Важный статус
дублируется текстом и не кодируется только цветом.

### 4.7 Прогресс и отмена

Длительная операция сразу сообщает, что она началась, показывает текущий этап и
своевременно реагирует на Ctrl-C. Отмена останавливает дочерний процесс, не
оставляет lock и не утверждает, что операция успешно завершилась.

## 5. Предлагаемая модель команд

Команды группируются по объектам платформы. Обзор `status` намеренно находится на
верхнем уровне: это cross-resource read model, а не операция над одним сервисом.

| Команда | Назначение |
|---|---|
| `platform status [SERVICE]` | Обзор платформы или состояние выбранного сервиса |
| `platform service list` | Краткий каталог сервисов без развёрнутой диагностики |
| `platform service create` | Создание сервиса из явных параметров или через мастер |
| `platform service deploy SERVICE` | Деплой с опциональными `--build`, `--pull`, `--dry-run` |
| `platform service stop SERVICE` | Остановка сервиса с подтверждением в TTY |
| `platform service restart SERVICE` | Перезапуск сервиса |
| `platform service logs SERVICE` | Просмотр логов, фильтры и follow |
| `platform diag validate` | Проверка конфигурации и состояния платформы |
| `platform diag server TARGET` | Диагностика сервиса или домена |
| `platform backup create/list/restore/delete` | Работа со снапшотами Master/Kopia |
| `platform proxy reload` | Перезагрузка Caddy |
| `platform info` | Версия CLI, обнаруженный project root и доступность зависимостей |

`platform status` не дублируется как `platform service status`. `service list`
остаётся компактным каталогом, а status показывает здоровье, источники данных и
проблемы. Поля «последний деплой» и «версия» не показываются, пока для них нет
авторитетного источника.

Примеры основных сценариев:

```bash
platform status
platform status api
platform service list --json
platform service deploy api --build --dry-run
platform service deploy api --build --yes --no-input
platform service logs api --since 15m --grep ERROR
platform service create --name my-api --visibility public \
  --routing domain --domain my-api.example.test --no-input
platform backup restore SNAPSHOT_ID --target api
```

Опции имеют одинаковый смысл во всех группах. Командные параметры формата и
фильтрации указываются после команды, например
`platform service list --json`. Help каждой команды явно показывает область
действия `--yes`, `--no-input`, `--verbose` и других общих опций.

## 6. Status как центральный сценарий

### 6.1 Секции

Предлагаемый набор секций:

| Секция | Источник | Содержимое |
|---|---|---|
| `services` | Discovery + Docker + Caddy | Сервис, статус, маршрут, URL |
| `health` | Кэш Master API, ограниченный direct fallback | Результат, источник, возраст и причина |
| `problems` | Лёгкие read-only проверки | Ошибки и предупреждения с объектом и следующей командой |
| `resources` | Docker и системные данные | Ограниченный обзор памяти, диска и логов |
| `backups` | Master API | Последний snapshot для backup-enabled сервисов |

Дефолт: `services`, `health`, `problems`. `resources` и `backups` доступны по
конфигурации и флагу секций. В выводе всегда явно виден перечень не загруженных
секций. Секция `problems` запускает только лёгкие read-only проверки и не
выполняет исправлений.

```yaml
# ${XDG_CONFIG_HOME:-~/.config}/platform/config.yml
status:
  sections: [services, health, problems]
  compact: false
```

Неизвестное имя секции даёт warning с перечнем допустимых значений. Значение,
переданное в `--sections`, перекрывает пользовательскую настройку.

### 6.2 Состояние и свежесть

Каждая секция имеет собственный результат: данные, состояние загрузки, источник,
время наблюдения и warnings. Общий status может быть частичным, но доступные
секции продолжают отображаться. Данные Master API, полученные из кэша, не
маскируются под текущую прямую проверку.

Если опциональный источник недоступен, человек видит частичный status и причину.
Для скриптов JSON содержит `complete: false` и список проблем. Exit code `3`
используется, когда для конкретной команды недоступна обязательная зависимость;
флаг `--strict` делает недоступность любой выбранной секции ненулевым результатом.

### 6.3 Обновление

`--watch` обновляет только те источники, для которых безопасен повторный запрос.
Прямые health-пробы не запускаются чаще заданного интервала и не превышают
командный deadline. Интервал refresh виден в help. Ctrl-C завершает watch без
traceback и с обычным кодом отмены процесса.

## 7. Архитектура

### 7.1 Границы и направление зависимостей

Предлагается разделить интерфейс, сценарии приложения, доменную политику и I/O.
Это уточняет исходные `commands/core/sources/ui`: источники и presentation являются
адаптерами вокруг application/domain, а не этажами одной цепочки импорта.

```text
                        +--------------------------+
                        | CLI adapter              |
                        | Typer/Click: args, help  |
                        +------------+-------------+
                                     |
                                     v
                        +--------------------------+
                        | Application use cases    |
                        | status, deploy, diag...  |
                        +------+---------------+---+
                               |               |
                               v               v
                        +-----------+   +----------------+
                        | Domain    |   | Ports          |
                        | models,   |   | runtime,       |
                        | policies  |   | routing, ...   |
                        +-----------+   +-------+--------+
                                                ^
                                                |
                                  +-------------+-------------+
                                  | Adapters                  |
                                  | filesystem, Compose,      |
                                  | Docker, Caddy, Master API |
                                  +---------------------------+

CLI adapter -> presenters: text / JSON / NDJSON
```

Правила зависимостей:

- CLI adapter разбирает ввод, вызывает use case и преобразует ожидаемые ошибки в
  exit code. Он не содержит бизнес-правил и не обращается сам к Docker/API.
- Application use cases координируют источники, deadlines, lock и результат
  операции. Они возвращают типизированный результат, а не строки для печати.
- Domain содержит модели и чистые правила: идентификаторы сервисов, finding,
  deployment plan и классификацию результата. Domain не импортирует Typer, Rich,
  Docker SDK, HTTP-клиент или файловый слой.
- Ports появляются только на границах, где есть разные backend-адаптеры,
  независимая деградация или важная тестовая подмена. Не нужен общий
  dependency-injection framework или универсальный registry источников.
- Adapters реализуют файловое обнаружение, Docker/Compose, чтение Caddy и Master
  API. Операции с процессами и сетью не размещаются в домене.
- Presenters принимают результат use case и форматируют его. Источники и домен
  не импортируют UI.
- Composition root собирает реализацию CLI один раз. В тестах заменяются порты,
  а не внутренние helper-имена CLI.

Пример простого контракта результата секции:

```text
SectionResult:
  state: complete | partial | unavailable
  data: typed value or absent
  source: filesystem | docker | caddy | master | direct_probe
  observed_at: timestamp or absent
  stale: boolean
  warnings: list of structured warnings
```

Не требуется заводить отдельный слой или универсальную базовую абстракцию для
каждой функции. Граница оправдана, когда даёт отдельную политику timeout,
fallback, тестирования или сериализации.

### 7.2 Предлагаемое размещение модулей

Можно сохранить знакомые верхнеуровневые каталоги, уточнив их обязанности:

```text
apps_platform/
├── cli.py                  # фабрика приложения и composition root
├── commands/               # application use cases
│   ├── status.py
│   ├── service.py
│   ├── diagnostics.py
│   └── backups.py
├── core/                   # доменные модели, ошибки и чистые правила
│   ├── models.py
│   ├── errors.py
│   └── validators/
├── sources/                # I/O adapters, сгруппированные по backend
│   ├── filesystem.py
│   ├── compose.py
│   ├── docker.py
│   ├── caddy.py
│   └── master.py
├── ui/                     # text/json renderers, prompts, progress
└── config.py               # загрузка настроек и project context
```

`compose_runner` переезжает из core в I/O adapter: он запускает внешний процесс.
Pure Caddy parsing может оставаться в core, но чтение файлов и определение их
путей принадлежат adapter. Это сохраняет полезные границы исходного предложения,
не делая саму инфраструктуру частью домена.

## 8. Источники данных и деградация

Источник выбирается по авторитетности и возможности работать независимо от
Master API.

| Данные/операция | Источник и поведение |
|---|---|
| Discovery и манифесты | Файловая система проекта; это source of truth для наличия сервиса |
| Deploy, stop, restart, logs | Docker/Compose напрямую; Master API не является prerequisite |
| Контейнерный статус и ресурсы | Docker SDK или структурированный CLI adapter с timeout |
| Routing | Локальные Caddy-конфиги; ошибка parser явно маркируется как неполные сведения |
| Health | Сначала свежесть кэшированного результата Master; bounded direct probe при fallback |
| Backups | Master API, поскольку Kopia управляется через него |

Каждый source вызов получает бюджет времени и возвращает источник, время,
свежесть и причину деградации. Отказ секции не маскирует отказ всей платформы.
Deploy postcheck требует свежего результата и не считает старую health-запись
доказательством успешного запуска.

До принятия решения об authoritative deployment metadata поля «последний деплой»
и «версия» не вычисляются из времени создания image. Image digest можно отдельно
показать как digest, но он не означает время деплоя.

## 9. Контракты CLI

### 9.1 Форматирование и потоки

- В обычном TTY вывод человекоориентированный. Таблицы адаптируются к ширине;
  если колонок не хватает, используется компактное представление, а не
  горизонтальный набор обрезанного текста.
- При перенаправлении stdout убираются цвета и анимация; записи остаются
  построчными. `NO_COLOR`, `TERM=dumb` и `--no-color` учитываются независимо от
  выбранного presenter.
- Успешный `--json` выдаёт только JSON в stdout. Human progress и warnings идут
  в stderr; JSON-ошибка имеет стабильную схему и тоже не смешивается с данными.
- `logs --follow --json` и `status --watch --json` выдают NDJSON: одна запись на
  одно событие/снимок. Следующий snapshot можно читать, не ожидая конца команды.
- В JSON обозначены schema version, timestamps с timezone, неполные секции,
  warnings и provenance. Текстовый формат не сериализуется обратно в JSON.

### 9.2 Взаимодействие и exit codes

| Код | Значение |
|---|---|
| `0` | Команда успешна; для status может содержать явно описанный partial result |
| `1` | Ошибка выполнения операции или сервиса |
| `2` | Ошибка аргументов/конфигурации команды, пользователь может исправить ввод |
| `3` | Обязательная для данной команды зависимость недоступна |
| `4` | `diag validate` завершился с findings уровня error |
| `130` | Операция прервана Ctrl-C |

`--strict` превращает неполный status в код `3`. Warnings без ошибок в
`diag validate` не используют код `4`. Контракт ошибок централизован, но код
выбирается по типу причины, а не по общему `AppError`.

`--yes` отвечает только на подтверждения. `--no-input` запрещает все prompts.
В интерактивном режиме prompts проверяют stdin TTY, поддерживают отмену и никогда
не удерживают mutation lock во время ожидания человека.

### 9.3 Ошибки для человека

Сообщение должно отвечать на четыре вопроса: что произошло, с каким объектом,
что CLI успел сделать, что можно проверить или запустить дальше. Traceback
показывается только при `--verbose`. Секреты, заголовки авторизации и значения
переменных окружения никогда не попадают в обычный или verbose-вывод.

## 10. Надёжность, безопасность и производительность

- Целевой бюджет `platform status`: до 2 секунд для 10 сервисов. Это общий
  deadline, а не сумма неограниченных timeout. По его истечении CLI показывает
  уже собранные секции и отмечает несобранные.
- Completion сервисов: не более 100 мс p95, без Docker-команд и сетевого запроса
  в горячем пути. Кэш допустим только с project identity, atomic write, безопасным
  поведением на повреждённом файле и stale fallback. Cache path берётся из
  `$XDG_CACHE_HOME` или `~/.cache`.
- Пользовательские CLI-настройки размещаются в
  `${XDG_CONFIG_HOME:-~/.config}/platform/config.yml`. Они содержат preferences,
  например набор status-секций, но не дублируют `.ops-config.yml` и не становятся
  source of truth для сервисных манифестов.
- Project root определяется явно: `--project-dir`, затем `OPS_PROJECT_ROOT`,
  затем документированный поиск проекта. При неоднозначности CLI показывает
  найденный root в `platform info` и даёт явный override.
- Внешние команды запускаются argv-массивом без shell interpolation, с заданным
  cwd и ограниченным временем выполнения. Timeout и stderr отражаются в
  диагностике без вывода секретов.
- Mutation lock scoped по сервису там, где это безопасно; отдельные глобальные
  операции имеют собственный lock. Lock берётся после prompt и первичной
  валидации, затем состояние перепроверяется внутри критической секции.
- Доступ к Docker socket рассматривается как привилегированный доступ к host;
  CLI не понижает и не скрывает эту границу безопасности.

## 11. Этапы и критерии готовности

Каждый этап оставляет приложение пригодным к использованию и имеет black-box
проверки контрактов, а не только линт и unit tests.

| Этап | Результат | Критерии выхода |
|---|---|---|
| P0. Решения | Командная грамматика, JSON/errors, status semantics, packaging strategy | Открытые решения, блокирующие P1/P2, закрыты и записаны |
| P1. Каркас | Composition root, error mapping, presenters, config context, test harness | Help, exit codes, stdout/stderr, TTY/non-TTY проходят CLI tests |
| P2. Наблюдение | `status`, `service list`, sources и partial results | Deadline, freshness/provenance, JSON schema и секции проверены |
| P3. Управление | Create/deploy/stop/restart и lock policy | dry-run, ошибки шагов, Ctrl-C и lock проверены на fake adapters |
| P4. Операционные команды | Logs и backup operations | Follow/NDJSON; restore сохраняет `target`/`force` semantics |
| P5. Диагностика и completion | validate, completion сервисов и snapshots | Диагностика согласована со status; cache scoped к проекту |
| P6. Server diagnostics и release | Порт `diagnose-server.sh`, watch, удаление legacy CLI | Wheel и Docker image содержат все runtime assets; parity подтверждён |
| P7. TUI | Решение о Textual dashboard | Отдельное решение по реальным сценариям и запросам пользователей |

Старый CLI и `ops` wrapper удаляются или объявляются deprecated только после
проверки parity по командам, обновления help/docs и проверки wheel/container
установок. До этого переход остаётся обратимым.

Для каждой фазы обязательны: unit tests домена, adapter tests с fixture/fake,
CLI subprocess tests, проверки схем JSON и TTY-поведения. Реальный сервер нужен
как smoke-test, но он не заменяет детерминированные тесты.

## 12. Риски и принятые компромиссы

| Риск или компромисс | Решение в предложении |
|---|---|
| Master API может не иметь endpoint свежего health | Кэш Master остаётся primary; bounded direct fallback явно маркируется |
| Нельзя честно показать deployment time из image digest | Не показывать поле до появления authoritative metadata |
| Caddy parser эвристический | Ограничить область поддержки, отображать неполноту, покрыть фикстурами |
| Docker/Compose меняет текстовый вывод | Не строить семантику на разборе progress text; изолировать адаптер и тестировать |
| Слишком много архитектурных слоёв | Ports только на реальных внешних границах; без framework и generic registry |
| Глобальный status может стать перегруженным | Секции конфигурируются, default остаётся коротким, `--compact` уменьшает детали |
| Временный shell-скрипт не входит в пакет | Проверка wheel/container обязательна до релиза команды |

## 13. Решения, которые надо подтвердить

1. Принять ли `platform status [SERVICE]` как исключение из object-grouping,
   чтобы status был естественной первой командой оператора.
2. Какой Master API endpoint или freshness contract авторитетен для health.
3. Нужны ли deployment metadata в v1; если да, какой backend является источником
   истины между несколькими CLI-клиентами.
4. Где будет поставляться и исполняться server diagnostic до завершения полного
   порта shell-скрипта.
5. Когда и каким сообщением объявлять `ops`/старые команды deprecated.

Пункты 1 и 2 блокируют фиксацию status-контракта. Пункт 3 блокирует поля
deployment version/time, но не должен блокировать базовый status. Пункт 4
блокирует выпуск `diag server` в пакетной установке.

## 14. Критерий успеха продукта

Оператор запускает `platform status` и за короткое время понимает, что работает,
что требует внимания, насколько свежи сведения и с чего безопасно продолжить.
Автоматизация запускает ту же операцию и получает машинно-читаемый результат без
неявного ввода. При недоступности Master API локальное управление продолжает
работать, а неполнота наблюдения явно обозначена.

Если для ответа нужно знать внутренний helper, угадывать источник значения,
обрабатывать нестабильный текстовый вывод или листать историю терминала, CLI не
выполнил свою продуктовую миссию.
